## WordPress REST API Autotests

Проект представляет собой автоматизированные API-тесты, построенные на микросервисной архитектуре. На данный момент
автоматизированы два полигона:

1. **WordPress REST API:** Полный цикл CRUD-операций над сущностью "Posts" с обязательной проверкой фактического 
изменения данных в БД MySQL через JDBC. Во втором сьюте тестовые данные создаются и удаляются напрямую в БД с помощью 
SQL-запросов.
2. **Yandex.Disk API:** Проверка авторизации по OAuth-токену, а также управление папками (создание, удаление,
восстановление из корзины).

### Технологический стек
- **Java:** 25
- **Сборщик:** Maven
- **Тестовый фреймворк:** TestNG
- **API-клиент:** REST Assured
- **Работа с БД:** JDBC (MySQL Connector)
- **Генерация данных:** JavaFaker
- **Конфигурация:** Owner
- **Дополнительно:** Lombok, Jackson

### Архитектура проекта 


Проект построен по принципу разделения ответственности и изолированности полигонов:
- `common` - общие настройки.
- `config` - менеджер конфигураций, раздающий специфичные настройки для каждого полигона.
- `wordpress` - изолированный полигон для тестов WordPress:
  - `config` - чтение `wordpress.properties` и `wp-test-data.properties`.
  - `db` - утилитный класс для взаимодействия с БД (JDBC), выполнения SQL-запросов и управления соединением.
  - `dto` - Data Transfer Objects для сериализации запросов и десериализации ответов API.
  - `endpoints` - хранение констант URL-эндпоинтов и настроек спецификации API.
  - `steps` - классы, инкапсулирующие логику отправки API-запросов.
  - `tests` - классы с автотестами и базовый класс с закрытием БД.
  - `utils` - вспомогательные классы для генерации данных и работы с БД.
- `yandex` - изолированный полигон для тестов Яндекс.Диска:
  - `config` - чтение `yandex.properties` и `yandex-test-data.properties`.
  - `dto` - Data Transfer Objects для десериализации ответов API.
  - `endpoints` - спецификации и эндпоинты.
  - `steps` - шаги запросов к API Диска.
  - `tests`- сьют проверок авторизации.
  - `utils` - вспомогательные классы для генерации данных.
### Предварительные требования

Для запуска проекта локально у вас должны быть установлены:

1. JDK 25
2. Apache Maven
3. Docker (для поднятия локального стенда WordPress и MySQL)

### Установка и запуск

**Шаг 1: Запуск локального стенда (для WordPress)**
1. Запустить Docker-контейнеры с WordPress и MySQL.
2. Дождитесь инициализации WordPress, задайте логин/пароль администратора при первичном входе.
3. Активируйте плагин JSON Basic Authentication в админ-панели WordPress.

**Шаг 2: Настройка конфигурации**
1. В проекте перейдите в `src/test/resources/configurations/`.
2. Скопируйте файлы `*.properties.example` в новые файлы без `.exmple` (`wordpress.properties` и `yandex.properties`).
3. Заполните их вашими актуальными данными (*Примечание: файлы `wordpress.properties` и `yandex.properties` добавлены в
`.gitignore` и не попадает в Git из соображений безопасности*):
    - `wordpress.properies` - доступ к WordPress API и БД MySQL.
    - `yandex.properties` - ваш Oauth токен Яндекс.Диска.

**Шаг 3: Запуск автотестов (Последовательный и Параллельный режимы)**

Проект поддерживает два режима запуска, управляемых переменной окружения `TEST_MODE`. По умолчанию используется 
последовательный запуск.

**Через IDE:** Нажмите правой кнопкой на файл `testng.xml` (или `testng-parallel.xml`) в папке `src/test/resources/` и
выберите `Run`. Либо запустите отдельный тестовый класс:
- Для WordPress: PostCrudTests.java или PostsGetTests.java.
- Для Яндекс.Диска: DiskAuthTests.java или FolderManagementTests.java

**Через консоль (Последовательный запуск):** Выполните в корне проекта команду:
```bash
mvn clean test
```

**Через консоль (Параллельный запуск):**
```bash
# Для PowerShell
$env:TEST_MODE="parallel"
mvn clean test

# Для Linux/Mac/Git bash
TEST_MODE=parallel
mvn clean test
```
В параллельном режиме сьюты WordPress и Яндекс.Диска выполняются одновременно в разных потоках. 

### Описание тест-кейсов

Сьют 1: `PostsCrudTests` CRUD-операции через API
1. `TC-001` Создание поста с валидными данными.
2. `TC-002` Редактирование поста (изменение статуса и заголовка).
3. `TC-003` Жесткое удаление поста (force=true).
4. `TC-004` Создание поста со значениями по умолчанию.
5. `TC-005` Безопасное удаление (перемещение в корзину без force).
6. `TC-006` Негативный: создание поста с невалидным статусом.
7. `TC-007` Негативный: редактирование несуществующего поста.
8. `TC-008` Негативный: удаление несуществующего поста.
9. `TC-009` Негативный: обновление поста с невалидным статусом.

Сьют 2: `PostsGetTests` получение данных через API, создание данных через JDBC
1. `TC-010` Получение данных поста по существующему ID.
2. `TC-011` Поиск постов по заголовку.
3. `TC-012` Поиск постов по контенту.
4. `TC-013` Фильтрация постов по валидному статусу.
5. `TC-014` Негативный: получение несуществующего поста.
6. `TC-015` Негативный: фильтрация постов по невалидному статусу.
7. `TC-016` Негативный: получение поста с невалидным форматом ID.

Сьют 3: `DiskAuthTests` Авторизация в API Яндекс.Диска
1. `TC-001` Авторизация с валидным OAuth-токеном.
2. `TC-002` Авторизация без токена.

Сьют 4: `FolderManagementTests` (Управление папками в Яндекс.Диске)
1. `TC-001` Успешное создание папки.
2. `TC-002` Создание папки по уже существующему пути.
3. `TC-003` Создание папки по несуществующему родительскому пути.
4. `TC-004` Запрос с пустым значением параметра `path`.
5. `TC-005` Запрос без параметра `path`.
6. `TC-006` Успешное удаление папки.
7. `TC-007` Удаление несуществующей папки.
8. `TC-008` Удаление папки с пустым значением параметра `path`.
9. `TC-009` Удаление уже удаленной папки (которая лежит в корзине).
10. `TC-010` Успешное восстановление папки (с поиском пути по хэшу).
11. `TC-011` Восстановление несуществующей папки из корзины.
12. `TC-012` Восстановление папки с пустым значением параметра `path`.
13. `TC-013` Конфликт при восстановлении папки (когда путь на Диске уже занят) 
с проверкой добавления суффикса `(1).`
